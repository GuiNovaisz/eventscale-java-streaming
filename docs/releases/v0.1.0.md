# EventScale v0.1.0 — Event Streaming Foundation

EventScale receives externally owned commerce lifecycle events, retains them in a partitioned Kafka log, and builds independent, reproducible PostgreSQL read models. This milestone is a durable event-streaming foundation, not an order transaction system or a work queue.

## Architecture and versions

HTTP API → durable PostgreSQL intake → keyed dispatcher → Kafka orders → transactional normalizer → normalized Kafka events → independent state and analytics groups → versioned PostgreSQL projections. New groups rebuild candidate projections from retained history before explicit activation. Deployables remain one Spring application, Kafka and PostgreSQL.

Java 21 LTS; Spring Boot 4.2.0; Spring Kafka 4.2.0; kafka-clients and Apache Kafka 4.4.0; PostgreSQL 18.7; Testcontainers 2.0.5; Maven Wrapper 3.9.12. Flyway/JDBC, Actuator/Micrometer, versioned JSON contracts, OpenAPI, Docker Compose and GitHub Actions complete the foundation. Application dependency versions were not upgraded for this release. Kafka uses KRaft; ZooKeeper is absent.

## Kafka topology

| Topic | Partitions / RF / minISR | Retention / cleanup | Producer | Consumer groups |
| --- | --- | --- | --- | --- |
| eventscale.orders.v1 | 3 / 1 / 1 | 7 days / delete | durable intake dispatcher | eventscale-normalizer-v1 |
| eventscale.order-events-normalized.v1 | 3 / 1 / 1 | 7 days / delete | transactional normalizer | order-state-projector-VERSION; analytics-projector-VERSION |
| eventscale.orders.dlt.v1 | 3 / 1 / 1 | 7 days / delete | transactional normalizer | administrative read_committed inspection |

Auto-create is disabled. LogAppendTime controls retention while occurredAt remains event time in the envelope. Message and decompressed-body limits remain 131072 bytes; API intake is bounded to 65536 bytes.

## Processing contracts

- aggregateId/orderId is the record key. Ordering is per aggregate/partition under the fixed topology, never global or automatic correction of incorrect business order. Two consumers per projection group distribute three partitions; groups receive the stream independently.
- Producer reliability uses acks=all, enable.idempotence=true, explicit retries and delivery/request timeouts. Protocol idempotence does not replace eventId business identity.
- Intake persists unique eventId/canonical content: equivalent content is idempotent; conflicting reuse returns 409. ACCEPTED acknowledges durable intake, not confirmed Kafka publication. The dispatcher acknowledgement/DB gap can physically duplicate records.
- Projectors disable auto-commit and acknowledge after a local JDBC transaction commits marker and mutation together. UNIQUE(version, consumer_name, event_id) makes PostgreSQL effects idempotent under at-least-once delivery, including the crash-after-DB-commit window.
- Kafka-native read-process-write uses Kafka transactions/EOS for output plus consumed offsets. read_committed hides aborted output. PostgreSQL does not automatically participate in this Kafka transaction or become distributed exactly-once.
- State derives lifecycle transitions; invalid business order is quarantined. Analytics independently counts facts and sums payment amounts by currency. It is cumulative, without windows or financial-ledger semantics.
- Deterministically invalid JSON/type/version records go to a transactional metadata-only DLT. A DLT outage retains source progress until publication can recover. Database infrastructure faults retry rather than being discarded as poison.
- Explicit OrderCreated v1/v2 contracts support an optional channel default while retaining v1 compatibility. Unsupported versions are classified; universal forward compatibility and registry governance are not claimed.
- Replay uses a new projection version and new groups at earliest retained input, followed by deterministic comparison and explicit activation. It does not destructively reset the live group's offsets.

## Validation, Docker and observability

The foundation suite contains 20 unit cases and 16 integration/failure scenarios (36 total). Real Kafka and PostgreSQL Testcontainers exercise ordering, independent groups and assignments, concurrent aggregates, duplicate effects, DB-commit crash/redelivery, broker/DB/DLT outages, poison continuation, v1/v2 compatibility, replay equivalence, rebalance, lag/catch-up and Kafka transaction commit/abort/read_committed. Failure scenarios are part of integration, not an additional fabricated test count. Release gates require zero failures/errors/skips; exact execution evidence is available in the release PR/main CI artifacts and [historical foundation evidence](../evidence.md).

Docker clean-start builds the non-root Java application, starts Kafka KRaft/PostgreSQL, runs Flyway, creates declared topics and waits for dependency readiness before the HTTP smoke. CI repeats verify and container clean-start/smoke/cleanup. Use `docker compose up -d --build --wait` and `pwsh ./scripts/smoke.ps1`; generate DB_PASSWORD only in the environment. `down -v` is for the disposable project's volumes only.

Prometheus exposes production/failures, consumption, duplicates, projection failures, DLT/quarantine, processing duration and per-group lag. Structured logs preserve event/correlation and Kafka coordinates without payload bodies. Identifiers are not metric labels. High lag can be healthy backlog; inspect errors and catch-up trend. See the [operations runbook](../operations.md).

## Limitations

RF1 and a single local broker/controller do not demonstrate HA or physical broker-loss tolerance. Replay cannot reconstruct events older than finite retention without a future archive/snapshot mechanism. No Schema Registry, Avro/Protobuf, multi-broker cluster, Kafka Connect, Debezium, cloud deployment or frontend is included. PostgreSQL projections remain outside Kafka EOS. Intake/dedup have no automatic purge; the dispatcher is intentionally serialized. The loopback-only local deployment has no public authentication/TLS design. No universal throughput benchmark or v0.2.0 functionality is claimed.

Source/tag, Maven Wrapper and Dockerfile are the reproducible release artifacts. No unnecessary JAR is attached to the GitHub Release.
